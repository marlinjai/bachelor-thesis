\chapter*{Abstract}\thispagestyle{empty}
% English abstract
When faced with the challenge of creating content and interactive web experiences, less technical users have to rely on \gls{CMS} like WordPress and \gls{WYSIWYG} editors.

Although these tools partially satisfy the needs of modern web experiences, many have limitations regarding the \gls{staticweb} they produce, and an inaccuracy between the preview layer and the final rendered content in the Web browser.

Due to the static output of tools like Webflow, WordPress, Wix, etc., users cannot make use of the \gls{SPA} features that come with modern JavaScript frameworks like React, NextJS or VueJS, which are based on the dynamic injection of JavaScript code during \gls{runtime}.

The following thesis answers the question of how a multilayered visual application builder allowing real-time \gls{UI} editing, dynamic CSS class generation, and multi-touch interactions can be implemented using the modern JavaScript framework NextJS. 

As a result, the barrier to build great software is lowered by applying meta-programming concepts.

Meta Programming is defined as follows:

"Meta-programs analyze, generate, and transform object programs. In this process, object programs are structured data."\footfullcite[p. 299]{visser2002}

In the context of this thesis, it is used to implement a program that dynamically generates other programs.

In specific SPAs during \gls{runtime}, by using a component based approach with drag and drop functionality and real-time \gls{UI} editing.

\chapter{Introduction}
\label{ch:introduction}

The development of content and interactive web experiences is a difficult task, especially for less technical users. In the early days of Web 1.0, developers worked with little more than HTML and CSS. Over time, however, the landscape grew increasingly complex. The proliferation of mobile computing devices—including smartphones, tablets, and wearables such as smartwatches—has significantly expanded the possibilities for digital interaction. However, it has also introduced intricate design challenges, notably the imperative for responsive design to accommodate diverse screen sizes and resolutions, as well as the complexities of multi-touch interactions.\cite{kim2021designpatternstradeoffsresponsive}

To address the mounting complexity inherent in modern web development, \gls{LCDP} such as Webflow, WordPress, and Wix have emerged. These platforms empower users to craft responsive and interactive web experiences without writing code. Leveraging visual interface builders with drag-and-drop component functionality, they abstract away the technical intricacies of responsive layout design and cross-device compatibility.

"An increasing number of software applications are being written by end users without formal 
software development training."\cite{kuhail2021characterizing} 
This inspired large technology companies [...] to invest in low-code development environments 
empowering end users to create web and mobile applications"\cite{kuhail2021characterizing}

With an annual growth rate of more than 20\% \gls{LCDP}s are expected to continue to grow up to a total market valuation of 50 billion USD by 2028.\cite{bratincevic2024lowcode}

This clearly shows the need for tools that allow users to create web applications without having to write code.


% 1.1 Visual Application Builder Overview
\section{Problem Statement}
\label{sec:visual-builder-overview}

The central problem addressed in this thesis lies in reconciling two fundamentally different requirements in the design of visual application builders:

\begin{enumerate}
  \item \textbf{Editor Reactivity}: Visual editors must provide immediate, synchronized feedback across multiple interface layers (e.g., component palette, canvas, layers panel, properties panel). User actions such as dragging components, modifying styles, or switching responsive breakpoints must instantly propagate to all relevant parts of the editor interface.
  \item \textbf{Runtime Interactivity}: At the same time, components within the application must preserve their intended runtime behavior. Buttons must remain clickable, forms must handle input and validation, and interactive elements must reflect accurate state management. This behavior must remain coherent both in the editor preview and in the exported application.
\end{enumerate}

Bridging these two reactive systems creates complex architectural constraints. 

Existing tools such as Framer and Webflow demonstrate the viability of multi-layered visual builders but typically achieve this by limiting developer control over the underlying framework. As a result, the expressive capabilities of React, particularly its component model, state management, and runtime flexibility, are only partially preserved.

This thesis does not seek to fully replicate the entirety of React's capabilities within a visual builder. Its goal is to investigate to what extent real-time UI editing can coexist with React's runtime architecture, and to identify the architectural patterns and meta-programming strategies that make this possible. By doing so, it addresses the gap between highly abstract visual editors and the framework-level fidelity required for professional application development.

% 1.3 Research Questions, Scope, and Contributions
\section{Research Questions, Scope, and Contributions}
\label{sec:research-objectives}

This thesis is guided by one overarching research question:

How can a multi-layered visual interface enable real-time application building while maintaining React interactivity through a meta-programming approach that transforms editor configurations into functional \gls{SPA} components?

Two supporting questions refine this investigation: (1) how can the four interface layers—the component palette, canvas, layers panel, and properties panel—remain synchronized in real time during visual editing operations, ensuring consistent editor reactivity? and (2) which architectural patterns enable the transformation of structured, serializable data into interactive React components?

The scope of the thesis is confined to the conceptual and technical exploration of architectural patterns and meta-programming approaches for a multi-layered visual application builder integrated with React. The goal is not to deliver a production-ready platform but to examine the feasibility of combining real-time editing with runtime interactivity, focusing on the tensions between editor reactivity and component behavior at runtime.

To pursue these questions, four technical objectives are defined:
\begin{enumerate}
  \item design of a unified component tree model that supports visual editing and React export
  \item development of a responsive preview system for desktop, tablet, and mobile viewports
  \item creation of a dynamic property editing interface adaptable to different component types
  \item implementation of a mechanism to extend the component palette with custom components
\end{enumerate}

The contributions of this research are both analytical and architectural. Analytically, it provides a structured problem analysis of the dual-reactivity challenge in visual application builders and offers a conceptual framework for organizing multi-layered interfaces around a unified component tree model. Architecturally, it identifies design patterns for transforming serialized editor configurations into interactive React components and examines the trade-offs between abstraction for accessibility and fidelity to the expressive power of React. Together, these contributions aim to advance the understanding of how real-time visual editing environments can be meaningfully combined with modern JavaScript frameworks, while also laying the foundation for future research and development in this domain.

% 2.1 Domain Knowledge and Context
\section{Domain Knowledge and Context}
\label{sec:domain-context}

Understanding the domain context is essential for positioning the multi-layered visual application builder within the broader ecosystem of development tools and user needs. This section reviews the current landscape of visual development platforms, outlining key solution categories and their limitations with respect to modern JavaScript frameworks. The analysis considers the rise of low-code platforms, the technical barriers faced by less-technical users, and the diverse stakeholder groups such builders must serve. These insights shape the architectural decisions and design priorities of the proposed system.

\subsection{Visual Application Development Landscape}

The landscape of visual application development has been fundamentally transformed by the emergence of \gls{LCDP}. As comprehensively analyzed by Sahay et al. \cite{sahay2020supporting}, these platforms represent a paradigm shift toward democratizing software development by reducing technical barriers through visual interfaces and model-driven approaches.

Traditional web development requires extensive technical knowledge of \gls{HTML}, \gls{CSS}, JavaScript, and modern frameworks like React or Vue.js. This technical barrier has historically limited content creators, designers, and non-technical users from building interactive web applications independently. 

\newpage
LCDPs address this challenge by providing \gls{WYSIWYG} interfaces that enable application creation through direct manipulation rather than code writing.

However, the current LCDP ecosystem reveals distinct categories with inherent architectural limitations:


\textbf{Static Site Builders} (WordPress, Godaddy, Squarespace): Generate static \gls{HTML} and \gls{CSS} output with limited interactivity and no true \gls{SPA} capabilities

\textbf{Design-to-Code Tools} (Webflow, Adobe XD): Excel in visual design fidelity but lack dynamic application logic and state management

\textbf{Component-Based Builders} (Framer, Bubble): Offer dynamic functionality through proprietary runtime systems, creating vendor lock-in challenges


The fundamental challenge identified by Sahay et al. lies in bridging the gap between visual design tools and modern JavaScript framework capabilities, particularly React's component-based architecture and dynamic state management. 


\subsection{Target User Groups and Stakeholders}

Visual application builders serve multiple stakeholder groups with varying technical backgrounds and requirements:

\begin{itemize}
    \item \textbf{Content Creators}: Need rapid and intuitive visual prototyping and landing page creation
    \item \textbf{Designers}: Require pixel-perfect visual control with responsive design capabilities
    \item \textbf{Developers}: Seek faster iteration cycles and visual debugging tools
    \item \textbf{Product Teams}: Need collaborative tools that bridge design and development workflows
    \item \textbf{Agencies}: Require scalable solutions for client work with quick turnaround times
\end{itemize}

Each group brings distinct requirements for interactivity levels, customization depth, and technical control, necessitating a flexible architecture that accommodates various use cases.

% 2.2 Related Work and Existing Solutions
\section{Related Work and Existing Solutions}
\label{sec:related-work}

This section examines existing visual application building platforms to understand current approaches, architectural patterns, and limitations. The analysis provides context for the proposed multi-layered approach and identifies gaps that this thesis addresses.

\subsection{Analysis of Current Visual Building Platforms}

The examination covers three categories of platforms: component-based visual development tools (Framer), design-centric approaches (Webflow), and code-first visual editing environments (Codux). Each platform represents different trade-offs between visual design capabilities, runtime interactivity, and technical flexibility.

\subsubsection{Framer: Component-Based Visual Development}

Framer represents the current state-of-the-art in visual application builders, combining design tools with React-based component rendering. Key architectural insights from Framer include:

\begin{itemize}
    \item \textbf{Runtime Component System}: Rather than generating static code, Framer maintains a centralized data model that drives dynamic React component rendering
    \item \textbf{Live Preview Architecture}: Changes to the visual interface immediately reflect in a live preview through reactive state management
    \item \textbf{Component Tree Model}: Applications are represented as hierarchical component trees with serializable state
    \item \textbf{Override System}: Developers can inject custom logic through JavaScript "overrides" that modify component behavior
\end{itemize}

However, Framer's proprietary nature limits extensibility and creates vendor lock-in for users seeking to migrate to standard React applications.

\subsubsection{Webflow: Design-Centric Approach}

Webflow focuses primarily on visual design with limited dynamic functionality:

\begin{itemize}
    \item \textbf{Static Output}: Generates traditional \gls{HTML} and \gls{CSS} with minimal JavaScript interactivity
    \item \textbf{Animation System}: Built-in animation tools but no true state management
    \item \textbf{CMS Integration}: Content management capabilities but no dynamic application logic
\end{itemize}

While Webflow excels in design fidelity, it cannot produce modern \gls{SPA} applications with complex state management and component interactions. It is rather focused on design and content management for static websites, and not on the development of interactive web applications.

\subsubsection{Codux: Code-First Visual Editing}

Codux is a visual IDE that works directly against a React codebase rather than a proprietary runtime. Key characteristics:

\begin{itemize}
    \item \textbf{Code generation/sync}: Visual edits generate React components and styles in the repo (no separate model runtime)
    \item \textbf{Lower lock-in}: Output is plain code, maintainable outside the tool
    \item \textbf{Developer-centric}: Fits Git workflows and code review practices
\end{itemize}

This contrasts with model-at-runtime platforms such as Framer, and provides useful context for the trade-offs summarized by Sahay et al. \cite{sahay2020supporting}.

\subsection{Low-Code Platform Reference Architecture}

Low-code platforms share a recurring architecture that aligns closely with this thesis's system design. The study by Sahay et al. \cite{sahay2020supporting} synthesizes common capabilities across platforms and proposes a conceptual architecture that provides useful context for understanding where visual builders fit within the broader ecosystem of development tools.

This subsection examines two complementary perspectives: 

\begin{itemize}
\item a layered architecture that separates concerns across application composition, service and data integration, and deployment  
\item a component-based architecture that details the specific services and modules enabling low-code functionality. Taken together, these reference models position the proposed multi-layered visual builder within established patterns while highlighting its unique contributions.
\end{itemize}

\newpage

Sahay et al. also propose a set of evaluation dimensions—such as user-interface tooling, interoperability, security, collaboration, reusability, scalability, business-logic tooling, build approach (code generation vs. model-at-runtime), deployment options, and target solution type—which expose trade-offs between accessibility and framework fidelity. These categories provide a backdrop for situating our system, particularly with respect to its treatment of the build process.

Figure~\ref{fig:lcdp-layers} illustrates the layered architecture: application composition at the top, service and data integration in the middle, and deployment at the base. Within this framework, our visual editor is situated primarily in the application layer (toolbox, canvas, properties panel, layers view), while integration and deployment remain outside its scope. One clarification is worth noting: in the context of a visual builder, deployment involves two distinct concerns—the deployment of the platform itself and the runtime deployment of user-generated applications (for example, publishing projects to custom domains). Although this thesis does not address deployment in detail, making this distinction highlights that platform hosting and application publishing represent separate architectural challenges, each warranting dedicated research and analysis. The focus here remains on the architectural problem of achieving real-time editor reactivity and runtime component generation within the application layer.

The component-based reference architecture in Figure~\ref{fig:lcdp-components} illustrates the sequential pipeline characteristic of most LCDPs. In this model, a graphical environment produces an abstract representation (often in XML), which is passed through a code generator to produce source code, then compiled before it can be deployed. \section{Relevant Technological Concepts}
\label{sec:technological-concepts}

This section establishes the technological foundations necessary for understanding the multi-layered visual application builder. Rather than providing exhaustive technical documentation, the focus is on core concepts that enable runtime component generation, reactive state management, and efficient visual editing interactions.

The technological landscape for visual builders spans several domains: React's component model and rendering architecture provide the foundation for dynamic UI generation; reactive programming paradigms enable efficient state synchronization across editor layers; and modern JavaScript meta-programming techniques allow treating component configurations as manipulable data structures. Understanding these concepts is essential for grasping how the proposed system bridges visual editing interfaces with functional React applications.

The following subsections introduce these concepts at a level accessible to readers with basic React and JavaScript knowledge, emphasizing their relevance to visual editor architecture rather than implementation specifics, which are detailed in Chapters 5 and 6.

\subsection{JavaScript DOM Manipulation}

The Document Object Model (DOM) emerged as a critical bridge between static HTML content and dynamic, interactive capabilities in web browsers. In the early web, pages were static renderings with no mechanism for post-load manipulation. With the advent of JavaScript in 1995, browser vendors introduced ad-hoc, proprietary APIs, such as document.layers in Netscape Navigator and document.all in Internet Explorer, to allow scripts to access and alter page content \cite{holzner2002insidejavascript}. These inconsistencies led to fragmentation and significant cross-browser compatibility issues. To resolve this, the W3C published the DOM Level 1 Recommendation in 1998, establishing a standardized interface for navigating and manipulating document structure and content \cite{w3c1998dom}. Subsequent iterations DOM Level 2 (2000) and DOM Level 3 (2004) expanded the model with event handling, CSS integration, and XML support, paving the way for richer web interactions \cite{w3c2000dom2, w3c2004dom3}.

The establishment of the DOM enabled a new paradigm of interactive web development. It allowed JavaScript to programmatically modify content, respond to user events, and adjust presentation dynamically, all without requiring a full page reload. This capability, in conjunction with the introduction of the XMLHttpRequest API in the early 2000s, made the Ajax model possible, which in turn fueled the rise of so-called "Web 2.0" applications with real-time, asynchronous updates \cite{garrett2005ajax}. The DOM's live, mutable tree structure thus became the foundation for modern reactive frameworks such as React, Angular, and Vue. In particular, React builds upon the DOM by introducing the virtual DOM, an in-memory representation of the UI that is efficiently reconciled with the real DOM, ensuring that only the necessary changes are applied to the interface. Without the DOM as both a programmable abstraction and rendering target, neither Ajax-driven interactivity nor the component-based architectures of today's frameworks would be feasible.

\subsection{React and its rendering pipeline}

React is a JavaScript library for building user interfaces that introduced a declarative programming model, where interfaces are described as trees of components rather than through imperative DOM manipulation. Components can either be primitive host elements such as a \texttt{div}, or user-defined functions and classes that themselves compose other components. At the heart of React’s architecture lies the idea of maintaining a virtual representation of this component tree and synchronizing it efficiently with the Document Object Model (DOM) whenever the underlying state or props change \cite{chavan2021jsx, reactdocs_virtualdom}. This abstraction makes React a compelling foundation for visual application builders, since it allows changes in configuration to be reflected as live, interactive updates without the need for manual DOM handling.

\subsubsection{JSX Compilation Pipeline}

One of React’s central innovations is JSX (JavaScript XML), a syntax extension that allows developers to write component structures in a markup-like form directly within JavaScript. Although JSX resembles HTML, it is not understood by browsers. Instead, it must be compiled, commonly via \gls{Babel}, into plain JavaScript. In earlier React versions, each JSX element was transformed into a call to \texttt{React.createElement}, returning an immutable \emph{ReactElement} object. These ReactElements encode the type, properties, and children of a node, forming the blueprint for React’s rendering process. \cite{reactdocs_jsx, react17_jsx_runtime}  

\begin{lstlisting}[language=JavaScript, caption={Legacy JSX to createElement Transformation}]
// JSX syntax
<button onClick={() => setCount(count + 1)}>
  {count}
</button>

// Compiled form (React <17)
React.createElement("button", 
  { onClick: () => setCount(count + 1) }, 
  count
);
\end{lstlisting}

With the introduction of React 17, a new \emph{JSX Transform} was released. Instead of compiling JSX into \texttt{React.createElement}, the compiler now emits calls to lightweight helper functions \texttt{jsx} and \texttt{jsxs} provided by the \texttt{react/jsx-runtime} entry point \cite{react17_jsx_runtime}. This removes the requirement to import React explicitly in every file and enables further optimizations in bundle size and tooling support.  

\begin{lstlisting}[language=Java, caption={New JSX Runtime Transformation (React 17+)}]
// JSX syntax
<button onClick={() => setCount(count + 1)}>
  {count}
</button>

// Compiled form (React 17+)
import { jsx as _jsx } from "react/jsx-runtime";

_jsx("button", { onClick: () => setCount(count + 1), children: count });
\end{lstlisting}

By treating JSX as declarative sugar for producing ReactElements, React decouples user interface specification from low-level DOM operations. The shift from \texttt{createElement} to the new runtime-based transform reflects React’s long-term strategy of simplifying developer experience and enabling runtime systems, such as visual builders, to generate components as structured data rather than through direct DOM manipulation.

\subsubsection{Virtual DOM and Reconciliation}

The React runtime operates by maintaining a Virtual DOM: an in-memory tree of ReactElements that mirrors the intended structure of the interface. When state or props change, React regenerates the relevant parts of this virtual tree and compares it against the previous version. Through its reconciliation process, React applies only the minimal set of mutations needed to update the real DOM, using heuristics that optimize for performance in common scenarios such as list reordering \cite{reactdocs_virtualdom, geeksforgeeks_reconciliation, guha2010programming}.  

For visual editors, this model is especially advantageous: interactions like moving a component, toggling a property, or reorganizing a hierarchy can be reflected immediately without re-rendering the entire interface. This efficiency is critical for delivering a responsive editing experience.

\subsubsection{React Fiber and Concurrent Rendering}

With React 16, the reconciliation engine was fundamentally redesigned under the name Fiber, introducing an asynchronous model of rendering. A fiber is a lightweight object representing a unit of work in the rendering pipeline. The system organizes these fibers into a “work-in-progress” tree that React processes incrementally before committing the final result to the DOM.  

Rendering is divided into two phases: an interruptible render phase (building the work-in-progress tree using \texttt{beginWork()} and \texttt{completeWork()}), and a synchronous commit phase (\texttt{commitWork()}), which applies mutations to the DOM. This split ensures that while updates can be scheduled flexibly, DOM consistency is always preserved \cite{react_fiber_explained, react_fiber_architecture}.  

Concurrent features enabled by Fiber, such as interruptible rendering, priority-based scheduling, and time-slicing, allow React to keep applications interactive even during large updates. For visual application builders, these capabilities are essential: dragging a component across a canvas or typing into a property panel can be prioritized over background re-renders, ensuring fluid responsiveness \cite{react_fiber_concurrent, cooper2021fiber}.  

Taken together, JSX, the Virtual DOM, and Fiber’s concurrent reconciliation establish React as a runtime that behaves like a real-time compiler of user interfaces. Each change to a component’s configuration is translated into a ReactElement tree, reconciled against the prior version, and rendered to the DOM with minimal overhead—providing live previews that feel immediate while retaining the power of a full programming model.


\subsection{Next.js Framework}

While React is a front-end library focused purely on rendering user interfaces in the browser, it does not provide features for routing, data fetching, or server-side logic. 
By contrast, Next.js is a full-stack framework built on top of React that combines a powerful front-end component model with a server runtime for handling backend concerns \cite{vercel_nextjs}. 

This distinction is essential: Next.js applications can define \emph{API routes} and server-side logic that run securely on the server, never exposed to the client. 
This includes tasks such as database queries, authentication flows, or calls to external APIs. 
The separation of concerns ensures that sensitive operations remain on the server, while the client receives only the data needed for rendering. 

For the purposes of this project, Next.js was chosen over plain React for several reasons:

\begin{itemize}
  \item \textbf{Full-stack capabilities}: API routes and server functions enable integrating databases and external services without exposing business logic to the client.
  \item \textbf{Hybrid rendering}: Components can be rendered server-side, statically, or client-side depending on context, improving performance and SEO. 
  \item \textbf{File-based routing}: Automatic routing simplifies the creation of multi-page editor interfaces.
  \item \textbf{Production-ready defaults}: Features such as code splitting, image optimization, and deployment pipelines reduce boilerplate and accelerate development.
\end{itemize}

In the context of a visual application builder, Next.js ensures that the editor can operate as a cohesive full-stack system: the user interface is rendered with React, while server-side logic (such as project persistence, authentication, and external API calls) is securely handled on the backend. 
This combination of declarative UI and server-side infrastructure makes Next.js the pragmatic choice for this thesis over a plain React setup.

\subsection{MobX and MobX State Tree Foundations}
\label{sec:mobx-mst}

To understand the state management backbone of our visual builder prototype, it is essential to
explore how MobX and MobX State Tree (MST) enable reactive, structured, and serializable state
handling.

\subsubsection{Reactive State with MobX}

MobX is a reactive state management library that implements the paradigm of \emph{Transparent Functional Reactive Programming (TFRP)} \cite{mobx_docs}. 
In this paradigm:
\begin{itemize}
    \item \textbf{Functional} – Derived values (e.g., computed properties or React component renders) are expressed as pure functions of observable state: given the same state, they always yield the same result.
    \item \textbf{Reactive} – When observables change, all dependent values and observers automatically update.
    \item \textbf{Transparent} – Dependency tracking is inferred automatically at runtime without the need for manual subscription logic.
\end{itemize}

\paragraph{Comparison with React’s Pull-Based Model.}
React employs a \emph{pull-based} model: when state changes, components re-render, pulling in fresh values and recomputing derived results. 
MobX, by contrast, implements a \emph{push-based} model: observables notify only the computations and components that actually depend on them. 

\begin{lstlisting}[language=JavaScript, caption={React Pull-Based State Derivation}]
function Cart() {
  const [items, setItems] = useState([]);

  // Derived value recalculated on every render
  const totalPrice = items.reduce((sum, item) => sum + item.price, 0);

  return (
    <div>
      <h3>Total: {totalPrice}</h3>
      <ul>{items.map(item => <li key={item.id}>{item.name}</li>)}</ul>
    </div>
  );
}
\end{lstlisting}

\begin{lstlisting}[language=JavaScript, caption={MobX Push-Based Transparent Reactivity}]
class Cart {
  items = [];
  constructor() { makeAutoObservable(this); }

  get totalPrice() {
    return this.items.reduce((sum, item) => sum + item.price, 0);
  }
}

const CartView = observer(({ cart }) => (
  <div>
    <h3>Total: {cart.totalPrice}</h3>
    <ul>{cart.items.map(item => <li key={item.id}>{item.name}</li>)}</ul>
  </div>
));
\end{lstlisting}

In React, \texttt{totalPrice} is recalculated on every render (pull). In MobX, it is cached and only recomputed when its dependencies change, and any observing component is automatically updated (push).

\subsubsection{What MST Adds to MobX}

MobX State Tree (MST) builds on MobX by introducing structured, typed state trees with built-in serialization capabilities. Key architectural features include:

\begin{itemize}
  \item \textbf{Living state trees}: MST represents application state as a live, mutable tree, enriched by runtime type information and strict update constraints \cite{mobx_docs}.
  \item \textbf{Snapshots and patching}: The tree can be serialized into immutable snapshots, enabling history tracking, time travel, and easy persistence \cite{mobx_docs}.
  \item \textbf{Typed models and actions}: Each node in the tree is defined via a model with its own actions—explicit methods to mutate state—ensuring traceability and type safety.
  \item \textbf{Reconciliation}: Applying a snapshot to an existing tree reuses existing nodes where possible, mimicking React’s diffing philosophy at the data layer.
\end{itemize}

\subsubsection{Decoupling Domain and UI}

One of MST’s main advantages is the decoupling of state and business logic from the user interface. 
Rather than co-locating state within React components (via hooks), MST encourages modeling the domain problem first: users, projects, or UI elements become structured models within the state tree. 
The UI layer then acts as a projection of this domain model. 
As Weststrate, the creator of MobX, argues, this makes it possible to treat the \emph{UI as an afterthought}, allowing applications to evolve around a well-modeled domain state \cite{weststrate_ui}.

The overall research approach can be described as iterative prototyping supported by exploratory research methods. \section{Exploratory Prototyping and AI-Assisted Research}

In the earliest stage, the development was highly experimental. While unstructured, this phase proved essential for quickly identifying technological opportunities and constraints. Tools such as version control and containerization were used to ensure reproducibility and maintainability. Coding conventions and automated checks supported consistency and quality during development.

Validation was conducted continuously throughout the iterative cycles. Functional validation involved both manual and automated testing, ensuring that each requirement defined in Chapter~4 was correctly implemented. Non-functional validation focused on measuring performance, maintainability, and scalability, which are particularly important for a multi-layered builder architecture. In addition, the prototype was compared against the features and limitations of existing solutions, which highlighted both its strengths and areas where further work would be needed. Documenting limitations and unresolved challenges was treated as an integral part of the validation process, laying the groundwork for the evaluation in Chapter~6.

  \section{Data Protection Aspects}

The research prototype processes only configuration data and does not involve personal information, thereby presenting minimal data protection risks under GDPR. Nevertheless, for future production-grade deployment, it is crucial to adopt established privacy frameworks such as \emph{Privacy by Design} and \emph{Data Minimization}. The principle of Data Minimization—collecting, retaining, and processing only the data strictly necessary for a specific purpose—is a cornerstone of effective data protection \cite{ganesh2024dataMinimization}. This aligns with broader Privacy by Design approaches, which emphasize embedding privacy considerations throughout the system lifecycle \cite{jezova2020privacyByDesign, danezis2015privacyByDesign}.

In the context of a multi-user or multi-project architecture, ensuring tenant isolation is essential to maintain data confidentiality and separation. Numerous studies recommend robust multi-tenancy isolation via architectural segregation—ranging from isolated schemas or databases to access control mechanisms grounded in RBAC or ABAC models \cite{chippagiri2025multiTenantSecurity, das2019multiTenantIsolation}. Additionally, prudent secret management and authentication mechanisms—such as rotating environment-level credentials and applying fine-grained access control—are foundational to system resilience.

While these privacy safeguards are outside the immediate scope of the feasibility prototype, they remain vital for future development cycles. Acknowledging and planning for these measures, proactively positions the architecture to meet regulatory expectations and build user trust in subsequent, production-focused iterations.

\section{Bridging Visual Editing and Runtime Interactivity}
\label{sec:bridging-challenge}

One of the challenges addressed by this thesis lies in conceptually exploring how \textbf{two distinct reactive systems} can be implemented.
Visual editors require immediate updates to their interface layers when users perform editing operations, while the components being edited must preserve their intended runtime behavior for both preview and final deployment.
This dual-reactivity requirement creates complex architectural constraints that will be explored in the following chapters.

The following subsections introduce these two reactive systems and their interaction patterns.

\subsection{System 1: Editor Reactivity}
The visual editor interface requires real-time updates when users:
\begin{itemize}
    \item Drag components between layers
    \item Modify styles in the properties panel
    \item Select different components for editing
    \item Switch between responsive breakpoints
\end{itemize}

These operations must immediately reflect in all interface layers:

\begin{itemize}
  \nopagebreak
  \item the canvas preview
  \item the selection overlay
  \item the layers panel
  \item the properties panel
\end{itemize}
ensuring consistent visual feedback during the editing process.

\newpage

\subsection{System 2: Runtime Component Interactivity}
Simultaneously, the components being edited must maintain their intended runtime behavior:
\begin{itemize}
    \item Buttons must handle click events and update their state
    \item Forms must manage input validation and submission
    \item Interactive elements must respond to user interactions
    \item Component state must persist and update appropriately
\end{itemize}

This runtime interactivity must function both in the live preview during editing and in the final exported application. While not the primary focus of this thesis, a baseline of runtime interactivity is assumed to validate coherence between the editor state and the rendered behavior.

\section{Core Technologies and Frameworks}
\label{sec:core-technologies}

The following sections consolidate the technical pillars that enable a visual, runtime-driven application builder to behave predictably and performant. Rather than listing technologies in isolation, we articulate why each choice fits the problem context and how the pieces interlock: the canvas establishes constant-time spatial interactions, React supplies a declarative rendering model, MobX-State-Tree (MST) provides fine-grained, serializable reactivity for a runtime-generated component graph, and drag-and-drop tooling bridges direct manipulation with a consistent underlying model.

\subsection{Canvas Architecture for Visual Editors}
The canvas is the spatial backbone of a visual editor. Conceptually, user intent (pan and zoom) should scale with the viewport, not the scene size. A naive approach that updates each element's screen position for every pan event yields \(O(n)\) DOM mutations per frame and quickly collapses under load. Instead, we maintain a single transform state \(\{\,\text{scale},\, \text{translateX},\, \text{translateY}\,\}\) and apply it to a container element. This shift converts pan/zoom into constant-time operations: the browser's compositor applies one matrix transform, and all child elements inherit the result.

To make this reliable and smooth, two implementation details matter. First, anchoring the transform with \texttt{transform-origin: top left} keeps the math stable and avoids counter-intuitive pivot drift during zoom---the coordinates remain linear and predictable relative to the canvas origin. Second, hinting the browser with \texttt{will-change: transform} ensures early GPU layer promotion so that the first interaction is as fluid as subsequent ones. In practice, the transform state is updated in a high-frequency path (using refs to avoid React re-renders), while UI feedback such as zoom readouts is throttled via \texttt{requestAnimationFrame}. This separation preserves 60fps interactions even as the component tree grows and the editor performs additional work (selection overlays, hit-testing, or guide rendering) in parallel.

\subsection{Reactive State Management with MobX-State-Tree}

Visual editors maintain a living component graph that changes at runtime: users create, reorder, and configure nodes while the preview renders those changes immediately. Managing this with local \texttt{useState} scatters state across many function components and ties reactivity to render order. It also becomes cumbersome to address cross-cutting concerns (undo/redo, snapshots, persistence) and to serialize the full application state for storage or sharing. Redux centralizes state but shifts complexity into boilerplate (actions, reducers, normalization) and still renders at component-granularity unless additional memoization and selectors are carefully introduced.

MST adopts reactive programming principles \cite{bainomugisha2013survey} in a way that aligns with a runtime-generated tree. State is modeled as observable objects with explicit actions; the tree is inherently serializable; and views subscribe to only the data they read. This yields two practical benefits for a visual editor. First, when a node deep in the tree updates, only the components that observed that part of the state re-render. Second, the entire editor state can be snapshotted, diffed (patches), and restored, enabling persistence, time-travel, and collaboration workflows without bespoke plumbing.

\subsubsection{Limitations of \texttt{useState} for Runtime Trees}
Local hooks excel for leaf-level UI but struggle when the structure itself is data. With \texttt{useState}, component boundaries define state ownership; adding or moving nodes often means hoisting state or threading props. Moreover, dynamic trees created from data (e.g., via \texttt{React.createElement}) cannot rely on compile-time hook ordering for stability. These constraints make it harder to treat the application as a single, serializable model.

\subsubsection{Redux vs MST: Architectural Trade-offs}
Redux offers deterministic state transitions but requires action types, reducers, and often normalized schemas to scale. Deriving fine-grained subscriptions typically needs memoized selectors; without them, changes high in the store can cause broad re-renders. MST embeds structure and actions together: the model is the schema, the instance is the store, and actions mutate state under strict rules. Observers subscribe at the field usage site, providing fine-grained invalidation with minimal boilerplate. The cost is adopting MST's modeling patterns, but the payoff is simpler serialization (snapshots), incremental updates (patches), and ergonomic undo/redo.

\subsubsection{Observer-Driven Granularity}
With MST and \texttt{observer}-wrapped React components, reactivity is demand-driven. During render, MobX tracks which observables are read; when any of those change, only the affected components re-render. In a visual editor, this means a property tweak in a single node updates its render and any dependent overlays, while unrelated parts of the tree remain untouched. Compared to a naive global re-render, this preserves responsiveness as projects scale.

\subsubsection{Serialization: Snapshots, Patches, and History}
MST exposes snapshot APIs to serialize the entire tree to JSON, and patch streams to represent incremental edits. This is a natural fit for editor features: autosave persists snapshots, collaboration can exchange patches, and undo/redo walks a bounded history stack. Because the renderer consumes the same model the editor manipulates, preview and persistence share a single source of truth.

\subsubsection{Observable State and Automatic Reactivity}
MST enables automatic reactivity without explicit hook dependencies:

\begin{lstlisting}[language=Java, caption={MST Observable State Example}]
const ComponentNode = types.model({
  id: types.string,
  type: types.string,
  props: types.map(types.frozen()),
  state: types.map(types.frozen()),
  children: types.array(types.late(() => ComponentNode))
}).actions(self => ({
  setState(key, value) {
    self.state.set(key, value);
  }
}));

// Automatic re-rendering when state changes
const node = ComponentNode.create({...});
node.setState("count", node.state.get("count") + 1);
\end{lstlisting}

\subsubsection{Serialization and Persistence}

MST provides built-in serialization capabilities essential for visual editors:

\begin{itemize}
    \item \textbf{Snapshots}: Complete application state can be serialized to JSON
    \item \textbf{Patches}: Incremental changes can be captured and applied
    \item \textbf{Undo/Redo}: State history can be managed through snapshot comparison
    \item \textbf{Collaboration}: Changes can be synchronized across multiple users
\end{itemize}

\subsection{Drag-and-Drop API and Libraries}
\label{sec:drag-drop-patterns}

Direct manipulation is central to usability in visual editors, but the native HTML5 API alone is insufficient: drag previews are hard to customize, behavior varies across browsers, touch input is not first-class, and event semantics do not align neatly with React. Modern libraries abstract these pitfalls and provide consistent UX primitives while keeping the model authoritative.

Among common choices, React DnD affords maximal flexibility and integrates well with complex nested targets, at the cost of ceremony. react-beautiful-dnd, while offering polished list interactions, is deprecated and narrow in scope. In contrast, dnd-kit adopts a sensor-based architecture (mouse, touch, keyboard) with strong accessibility defaults and composable building blocks, making it a pragmatic fit for an editor that spans tree reordering, palette-to-canvas drops, and in-canvas rearrangements. The foundational ideas of snap-dragging remain relevant \cite{bier1986snap}: constraints and alignment hints improve precision and efficiency during manipulation.

Preserving model integrity is non-negotiable. All drag-and-drop operations must be expressed as MST actions (insert, reorder, remove), so that the component tree remains the single source of truth. The selection overlay and properties panel subscribe to the same model, ensuring that a drop immediately reflects in hierarchy, selection, and preview without bespoke synchronization. For external files, native \texttt{onDrop} and \texttt{onDragOver} handlers on dedicated zones complement UI drag-and-drop libraries, retaining OS integration while the application model mediates how assets enter the project \cite{szyperski1996component}.

\section{Meta-Programming Concepts and Patterns}
\label{sec:meta-programming}

\subsection{Theoretical Foundation}

Meta-programming, as defined by Visser (2002), involves programs that "analyze, generate, and transform object programs. In this process, object programs are structured data" \cite{visser2002}. This approach has been further developed in generative programming methodologies by Czarnecki and Eisenecker \cite{czarnecki2000generative}, who demonstrate how meta-programming enables the systematic generation of software families. 

In the context of visual application builders, this translates to systems that manipulate component configurations as data structures and transform them into executable React applications.

\subsection{Component Configuration as Data}

The meta-programming approach treats component definitions as serializable data structures rather than static code:

\begin{lstlisting}[language=Java, caption={Component Configuration Data Structure}]
const buttonConfig = {
  id: "button-1",
  type: "button",
  props: {
    className: "primary-button",
    children: "Click Me"
  },
  state: {
    count: 0,
    isActive: false
  },
  interactions: [
    {
      trigger: "onClick",
      action: "() => setState('count', state.count + 1)"
    }
  ]
};
\end{lstlisting}

\subsection{Runtime Component Generation}

These configurations are transformed into functional React components at runtime:

\begin{lstlisting}[language=Java, caption={Meta-Programming Component Transformation}]
function createRuntimeComponent(config) {
  return function RuntimeComponent() {
    const [state, setState] = useState(config.state);
    
    const handlers = config.interactions.reduce((acc, interaction) => {
      acc[interaction.trigger] = new Function(
        'state', 'setState', 
        `return (${interaction.action})`
      )(state, setState);
      return acc;
    }, {});
    
    return React.createElement(
      config.type,
      { ...config.props, ...handlers },
      config.props.children
    );
  };
}
\end{lstlisting}

This approach enables visual editors to generate fully functional components without requiring traditional compilation steps, supporting real-time editing and preview capabilities.
