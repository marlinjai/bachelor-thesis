\chapter*{Abstract}\thispagestyle{empty}
% English abstract
When faced with the challenge of creating content and interactive web experiences, less technical users have to rely on \gls{CMS} like WordPress and \gls{WYSIWYG} editors.

Although these tools partially satisfy the needs of modern web experiences, many have limitations regarding the \gls{staticweb} they produce, and an inaccuracy between the preview layer and the final rendered content in the Web browser.

Due to the static output of tools like Webflow, WordPress, Wix, etc., users cannot make use of the \gls{SPA} features that come with modern JavaScript frameworks like React, NextJS or VueJS, which are based on the dynamic injection of JavaScript code during \gls{runtime}.

The following thesis answers the question of how a multilayered visual application builder allowing real-time \gls{UI} editing, dynamic CSS class generation, and multi-touch interactions can be implemented using the modern JavaScript framework NextJS. 

As a result, the barrier to build great software is lowered by applying meta-programming concepts.

Meta Programming is defined as follows:

% TODO: ask if this is correct
"Meta-programs analyze, generate, and transform object programs. In this process, object programs are structured data."\footfullcite[p. 299]{visser2002}

In the context of this thesis, it is used to implement a program that dynamically generates other programs.

In specific SPAs during \gls{runtime}, by using a component based approach with drag and drop functionality and real-time \gls{UI} editing.

\section{Visual Application Builder Overview}
\label{sec:visual-builder-overview}

This thesis presents a \textbf{multi-layered visual application builder} that enables real-time \gls{UI} editing while maintaining full React functionality. The system consists of four integrated interface layers working in concert to provide comprehensive visual development capabilities:

\begin{enumerate}
    \item \textbf{Component Palette}: Drag-and-drop library of available UI components
    \item \textbf{Canvas with Responsive Preview}: Main editing area with desktop, tablet, and mobile viewports
    \item \textbf{Layers Panel}: Hierarchical tree view of component structure and relationships
    \item \textbf{Properties Panel}: Dynamic style and behavior editor for selected components
\end{enumerate}

\begin{figure}[h]
    \centering
    \includegraphics[width=0.95\textwidth]{images/Framer_multi_device_interface.png}
    \caption{Framer Interface showing multi-layered visual editing environment with layers panel (left), responsive canvas (center), properties panel (right), and component palette (top - currently not shown)\cite{framer}}
    \label{fig:framer-interface}
\end{figure}

As demonstrated in Figure~\ref{fig:framer-interface}, existing tools like Framer already implement variations of this multi-layered approach, showing the practical viability of such interfaces for visual application development.

% 1.2 Multi-Layered Interface Architecture
\newpage
\section{Multi-Layered Interface Architecture}
\label{sec:interface-architecture}

\subsection{Component Palette and Canvas Integration}

The \textbf{component palette} provides a library of reusable UI elements—buttons, forms, containers, text components—that users drag onto the main \textbf{canvas}. Unlike traditional drag-and-drop builders that generate static markup, this system creates dynamic component configurations that maintain React's interactive capabilities.

The \textbf{canvas} serves as the primary visual editing surface, featuring three responsive preview modes:

\begin{itemize}
    \item \textbf{Desktop View}: Full-width layout for standard web applications
    \item \textbf{Tablet View}: Medium-width responsive breakpoint (768px-1024px)
    \item \textbf{Mobile View}: Narrow layout for mobile-optimized interfaces (<768px)
\end{itemize}

Each viewport provides real-time preview of how the application will appear across different device types, with responsive styling automatically managed through the visual interface.

\subsection{Layers Panel: Component Tree Management}

The \textbf{layers panel} presents a hierarchical tree view of the component structure, enabling users to:

\begin{itemize}
    \item Navigate complex nested component relationships
    \item Reorder components through drag-and-drop operations
    \item Select components for editing without clicking on the canvas
    \item Manage component visibility and locking states
    \item Organize components into logical groupings
\end{itemize}

This panel reflects the underlying \textbf{component tree model}—a serializable data structure that maintains the complete application state including component relationships, properties, and interaction definitions.

\newpage
\subsection{Properties Panel: Dynamic Component Configuration}

The \textbf{properties panel} provides context-sensitive editing interfaces that adapt based on the currently selected component type. For each component, users can configure:

\begin{itemize}
    \item \textbf{Visual Styles}: Colors, typography, spacing, layout properties through intuitive controls
    \item \textbf{Content}: Text, images, and media through direct editing interfaces
    \item \textbf{Component State}: Initial values for interactive elements \\ (form inputs, counters, toggles)
    \item \textbf{Interactions}: Click handlers, hover effects, and user-defined JavaScript actions
    \item \textbf{Responsive Behavior}: Device-specific styling and layout adaptations
\end{itemize}

The panel dynamically generates appropriate input controls—color pickers for colors, number inputs for dimensions, dropdown menus for predefined options—based on the selected component's schema.

% 1.3 The Challenge: Bridging Visual Editing and Runtime Interactivity
\section[The Challenge: Bridging Visual Editing and Runtime Interactivity]{The Challenge: Bridging Visual Editing and\\Runtime Interactivity}
\label{sec:bridging-challenge}

The fundamental challenge addressed by this thesis lies in maintaining \textbf{two distinct reactive systems} that must work in perfect synchronization:

\subsection{System 1: Editor Reactivity}
The visual editor interface requires real-time updates when users:
\begin{itemize}
    \item Drag components between layers
    \item Modify styles in the properties panel
    \item Select different components for editing
    \item Switch between responsive breakpoints
\end{itemize}

These operations must immediately reflect in all interface layers:

\begin{itemize}
  \nopagebreak
  \item the canvas preview
  \item the selection overlay
  \item the layers panel
  \item the properties panel
\end{itemize}
ensuring consistent visual feedback during the editing process.

\subsection{System 2: Runtime Component Interactivity}
Simultaneously, the components being edited must maintain their intended runtime behavior:
\begin{itemize}
    \item Buttons must handle click events and update their state
    \item Forms must manage input validation and submission
    \item Interactive elements must respond to user interactions
    \item Component state must persist and update appropriately
\end{itemize}

This runtime interactivity must function both in the live preview during editing and in the final exported application.

\subsection{Visual Application Development Landscape}

The landscape of visual application development has been fundamentally transformed by the emergence of \gls{LCDP}s. As comprehensively analyzed by Sahay et al. \cite{sahay2020supporting}, LCDPs represent a paradigm shift toward democratizing software development by reducing technical barriers through visual interfaces and model-driven approaches.

Traditional web development requires extensive technical knowledge of \gls{HTML}, \gls{CSS}, JavaScript, and modern frameworks like React or Vue.js. This technical barrier has historically limited content creators, designers, and non-technical users from building interactive web applications independently. 

LCDPs address this challenge by providing \gls{WYSIWYG} interfaces that enable application creation through direct manipulation rather than code writing.

However, the current LCDP ecosystem reveals distinct categories with inherent architectural limitations:

\begin{itemize}
    \item \textbf{Static Site Builders} (WordPress, Godaddy, Squarespace): Generate static \gls{HTML}/\gls{CSS} output with limited interactivity and no true \gls{SPA} capabilities
    \item \textbf{Design-to-Code Tools} (Webflow, Adobe XD): Excel in visual design fidelity but lack dynamic application logic and state management
    \item \textbf{Component-Based Builders} (Framer, Bubble): Offer dynamic functionality through proprietary runtime systems, creating vendor lock-in challenges
\end{itemize}

The fundamental challenge identified by Sahay et al. lies in bridging the gap between visual design tools and modern JavaScript framework capabilities, particularly React's component-based architecture and dynamic state management. 

This thesis addresses this gap by proposing a meta-programming approach that maintains full React interactivity while providing visual editing capabilities.

\subsection{Target User Groups and Stakeholders}

Visual application builders serve multiple stakeholder groups with varying technical backgrounds and requirements:

\begin{itemize}
    \item \textbf{Content Creators and Marketers}: Need rapid prototyping and landing page creation without technical dependencies
    \item \textbf{Designers}: Require pixel-perfect visual control with responsive design capabilities
    \item \textbf{Frontend Developers}: Seek faster iteration cycles and visual debugging tools
    \item \textbf{Product Teams}: Need collaborative tools that bridge design and development workflows
    \item \textbf{Agencies and Freelancers}: Require scalable solutions for client work with quick turnaround times
\end{itemize}

Each group brings distinct requirements for interactivity levels, customization depth, and technical control, necessitating a flexible architecture that accommodates various use cases.

% 2.2 Related Work and Existing Solutions
\section{Related Work and Existing Solutions}
\label{sec:related-work}

\subsection{Analysis of Current Visual Building Platforms}

\subsubsection{Framer: Component-Based Visual Development}

Framer represents the current state-of-the-art in visual application builders, combining design tools with React-based component rendering. Key architectural insights from Framer include:

\begin{itemize}
    \item \textbf{Runtime Component System}: Rather than generating static code, Framer maintains a centralized data model that drives dynamic React component rendering
    \item \textbf{Live Preview Architecture}: Changes to the visual interface immediately reflect in a live preview through reactive state management
    \item \textbf{Component Tree Model}: Applications are represented as hierarchical component trees with serializable state
    \item \textbf{Override System}: Developers can inject custom logic through JavaScript "overrides" that modify component behavior
\end{itemize}

However, Framer's proprietary nature limits extensibility and creates vendor lock-in for users seeking to migrate to standard React applications.

\subsubsection{Webflow: Design-Centric Approach}

Webflow focuses primarily on visual design with limited dynamic functionality:

\begin{itemize}
    \item \textbf{Static Output}: Generates traditional \gls{HTML}/\gls{CSS} with minimal JavaScript interactivity
    \item \textbf{Animation System}: Built-in animation tools but no true state management
    \item \textbf{CMS Integration}: Content management capabilities but no dynamic application logic
\end{itemize}

While Webflow excels in design fidelity, it cannot produce modern \gls{SPA} applications with complex state management and component interactions. It is rather focused on design and content management for static websites, and not on the development of interactive web applications.

\subsubsection{Codux: Code-First Visual Editing}

Codux is a visual IDE that works directly against a React codebase rather than a proprietary runtime. Key characteristics:

\begin{itemize}
    \item \textbf{Code generation/sync}: Visual edits generate React components and styles in the repo (no separate model runtime)
    \item \textbf{Lower lock-in}: Output is plain code, maintainable outside the tool
    \item \textbf{Developer-centric}: Fits Git workflows and code review practices
\end{itemize}

This contrasts with model-at-runtime platforms such as Framer, and provides useful context for the trade-offs summarized by Sahay et al. \cite{sahay2020supporting}.

% 2.3 Core Technologies and Frameworks
\section{Core Technologies and Frameworks}
\label{sec:core-technologies}

\subsection{React Ecosystem and Virtual DOM Architecture}

React provides the foundational technology stack for dynamic component rendering and state management in visual application builders.

\subsubsection{JSX Compilation and createElement}

JSX syntax provides a declarative way to describe component structures:

\begin{lstlisting}[language=Java, caption={JSX to createElement Transformation}]
// JSX syntax
<button onClick={() => setCount(count + 1)}>
  {count}
</button>

// Compiled to React.createElement
React.createElement("button", 
  { onClick: () => setCount(count + 1) }, 
  count
);
\end{lstlisting}

This transformation enables dynamic component generation at runtime, where component configurations can be stored as data structures and rendered programmatically without requiring build-time compilation.

\subsubsection{Virtual DOM and Reconciliation}

React's Virtual DOM provides efficient updates through a diffing algorithm that minimizes actual DOM manipulations:

\begin{enumerate}
    \item Component state changes trigger re-rendering
    \item New Virtual DOM tree is generated via \texttt{createElement}
    \item React compares (diffs) previous and current Virtual DOM trees
    \item Minimal set of DOM mutations is computed and applied
\end{enumerate}

This architecture enables real-time preview updates in visual editors without performance degradation, as only changed components require DOM updates.

\subsubsection{React Fiber and Concurrent Features}

React Fiber represents a fundamental architectural redesign of React's reconciliation engine, introduced as the default reconciler since React 16 \cite{geeksforgeeks2025fiber}. Unlike the previous synchronous "Stack" reconciler, Fiber introduces asynchronous rendering capabilities essential for complex visual editors.

\paragraph{Fiber Architecture Overview}
A fiber is a plain JavaScript object representing a unit of work in React's rendering process. The architecture operates through two distinct phases:

\begin{enumerate}
    \item \textbf{Render Phase (Asynchronous)}: Processes fiber nodes through \texttt{beginWork()} and \texttt{completeWork()} functions. This phase can be interrupted, paused, or discarded.
    \item \textbf{Commit Phase (Synchronous)}: Executes \texttt{commitWork()} to apply DOM changes. This phase cannot be interrupted to maintain UI consistency.
\end{enumerate}

\paragraph{Concurrent Features for Visual Editors}
React Fiber provides capabilities crucial for visual editors \cite{geeksforgeeks2025fiber}:

\begin{itemize}
    \item \textbf{Interruptible Rendering}: Large component trees can be rendered incrementally without blocking user interactions
    \item \textbf{Priority-Based Updates}: User interactions (high priority) are processed before background operations (low priority)
    \item \textbf{Time Slicing}: Work is split into chunks using \texttt{requestAnimationFrame()} and \texttt{requestIdleCallback()}, preventing UI blocking during complex re-renders
    \item \textbf{Work Scheduling}: Tasks can be paused, resumed, or discarded based on priority and available time
\end{itemize}

\paragraph{Dual Tree Structure}
Fiber maintains two tree structures to enable non-blocking updates:

\begin{itemize}
    \item \textbf{Current Tree}: Represents the currently rendered UI state
    \item \textbf{Work-in-Progress Tree}: Contains pending changes and updates
\end{itemize}

React performs all modifications on the work-in-progress tree, then atomically swaps pointers to make it the current tree, ensuring UI consistency throughout the update process.

This architecture enables real-time preview updates in visual editors without performance degradation, as component updates can be prioritized and scheduled efficiently based on user interaction patterns.

\subsection{Reactive State Management with MobX-State-Tree}

Traditional React state management through \texttt{useState} hooks presents limitations for dynamic, runtime-generated component structures. Reactive programming paradigms, as surveyed by Bainomugisha et al. \cite{bainomugisha2013survey}, provide alternative approaches for managing complex state dependencies. 

MobX-State-Tree (MST) implements these reactive principles and is better suited for visual editors requiring dynamic component generation.

\subsubsection{Observable State and Automatic Reactivity}

MST enables automatic reactivity without explicit hook dependencies:

\begin{lstlisting}[language=Java, caption={MST Observable State Example}]
const ComponentNode = types.model({
  id: types.string,
  type: types.string,
  props: types.map(types.frozen()),
  state: types.map(types.frozen()),
  children: types.array(types.late(() => ComponentNode))
}).actions(self => ({
  setState(key, value) {
    self.state.set(key, value);
  }
}));

// Automatic re-rendering when state changes
const node = ComponentNode.create({...});
node.setState("count", node.state.get("count") + 1);
\end{lstlisting}

\subsubsection{Serialization and Persistence}

MST provides built-in serialization capabilities essential for visual editors:

\begin{itemize}
    \item \textbf{Snapshots}: Complete application state can be serialized to JSON
    \item \textbf{Patches}: Incremental changes can be captured and applied
    \item \textbf{Undo/Redo}: State history can be managed through snapshot comparison
    \item \textbf{Collaboration}: Changes can be synchronized across multiple users
\end{itemize}

% 2.4 Meta-Programming Concepts and Patterns
\section{Meta-Programming Concepts and Patterns}
\label{sec:meta-programming}

\subsection{Theoretical Foundation}

Meta-programming, as defined by Visser (2002), involves programs that "analyze, generate, and transform object programs. In this process, object programs are structured data" \cite{visser2002}. This approach has been further developed in generative programming methodologies by Czarnecki and Eisenecker \cite{czarnecki2000generative}, who demonstrate how meta-programming enables the systematic generation of software families. 

In the context of visual application builders, this translates to systems that manipulate component configurations as data structures and transform them into executable React applications.

\subsection{Component Configuration as Data}

The meta-programming approach treats component definitions as serializable data structures rather than static code:

\begin{lstlisting}[language=Java, caption={Component Configuration Data Structure}]
const buttonConfig = {
  id: "button-1",
  type: "button",
  props: {
    className: "primary-button",
    children: "Click Me"
  },
  state: {
    count: 0,
    isActive: false
  },
  interactions: [
    {
      trigger: "onClick",
      action: "() => setState('count', state.count + 1)"
    }
  ]
};
\end{lstlisting}

\subsection{Runtime Component Generation}

These configurations are transformed into functional React components at runtime:

\begin{lstlisting}[language=Java, caption={Meta-Programming Component Transformation}]
function createRuntimeComponent(config) {
  return function RuntimeComponent() {
    const [state, setState] = useState(config.state);
    
    const handlers = config.interactions.reduce((acc, interaction) => {
      acc[interaction.trigger] = new Function(
        'state', 'setState', 
        `return (${interaction.action})`
      )(state, setState);
      return acc;
    }, {});
    
    return React.createElement(
      config.type,
      { ...config.props, ...handlers },
      config.props.children
    );
  };
}
\end{lstlisting}

This approach enables visual editors to generate fully functional components without requiring traditional compilation steps, supporting real-time editing and preview capabilities.

% 2.5 Drag-and-Drop Interface Patterns
\section{Drag-and-Drop Interface Patterns}
\label{sec:drag-drop-patterns}

\subsection{HTML5 Drag and Drop API Limitations}

The native HTML5 Drag and Drop API provides basic functionality but has several limitations for complex visual editors:

\begin{itemize}
    \item Limited customization of drag feedback
    \item Inconsistent behavior across browsers
    \item No support for touch devices
    \item Difficulty integrating with React's event system
\end{itemize}

\subsection{React Drag-and-Drop Libraries}

Modern React applications typically use specialized libraries that provide better integration and functionality than native HTML5 drag-and-drop APIs. The foundational work on snap-dragging by Bier and Stone \cite{bier1986snap} established key principles for direct manipulation interfaces that continue to influence modern drag-and-drop implementations.

The \textbf{dnd-kit} library provides a modern, accessible approach to drag-and-drop with sensor-based architecture, separate sensors for mouse, touch, and keyboard input, built-in accessibility support, and extensive customization options for drag feedback and animations.

Drag-and-drop operations in visual editors must maintain component tree integrity through careful handling of tree structure updates and MST reactivity triggers, following established patterns in component-based software engineering \cite{szyperski1996component}.
